# 값으로 빠르게 찾아야 할 때

> [!question] 언제 이 노트를 보나
> 리스트에서 `.index()` 나 `in` 을 반복해서 쓰고 있는데, 입력이 커지면 느려지는 문제.

## 결론 먼저

| 상황 | 선택 |
|---|---|
| "이 값이 리스트 어디 있지?" 를 반복 조회 | list 대신 **dict** — 값 → 인덱스를 미리 저장 |
| "이 값을 본 적 있나?" 만 확인 | **set** |
| 값별로 개수·누적값을 세야 함 | **dict** (`collections.Counter` 도 가능) |
| 값 → 위치, 위치 → 값 을 **둘 다** 반복 조회 | **list + dict 를 짝으로 유지** (아래 참고) |

## 왜 list.index() 가 문제가 되나

`list.index(x)` 는 앞에서부터 하나씩 비교한다. 리스트 길이가 n이면 최악의 경우 n번 비교 → O(n).
이 조회를 반복문 안에서 m번 하면 전체는 O(n × m). n과 m이 둘 다 커지면 급격히 느려진다.

> [!tip] 알아채는 신호
> 채점 결과에서 작은 입력은 빠른데 큰 입력에서만 시간 초과가 나고, **입력이 커지는 폭보다 실행 시간이 훨씬 가파르게 늘어난다면** → 반복문 안의 `.index()` 나 `in list` 를 의심한다.

## 언제 쓰지 말아야 하나

- 값을 딱 한 번만 찾으면 된다. dict를 만드는 비용(O(n)) 자체가 낭비 — 그냥 한 번 순회
- 리스트가 원래 작다(수십 개 이하). O(n)이든 O(1)이든 체감 차이가 없다
- **순서·위치 자체가 중요한 조회.** dict는 키로 즉시 접근은 빠르지만 "몇 번째인지"는 따로 관리해야 한다 → 아래 [양방향이 필요하면](#양방향이-필요하면--두-개를-짝으로-유지한다)

## 구현 골격

```python
index_of = {value: i for i, value in enumerate(lst)}
pos = index_of[target]        # O(1)
```

```python
seen = set(lst)
if target in seen:            # O(1)
    ...
```

## 양방향이 필요하면 — 두 개를 짝으로 유지한다

dict로 바꿨는데도 여전히 느리다면, **병목이 사라진 게 아니라 반대편으로 옮겨간 것**일 수 있다.

리스트도 dict도 **한 방향만 빠르다.**

| | 위치 → 값 | 값 → 위치 |
|---|---|---|
| list | **O(1)** `lst[3]` | O(n) `lst.index(x)` |
| dict | O(n) 전체 스캔 | **O(1)** `d[x]` |

그래서 dict로 갈아타면 `.index()` 는 없어지지만, 이번엔 **"3번 자리에 누가 있지?"** 를 물어야 할 때
`next((k for k, v in d.items() if v == 3), None)` 같은 전체 스캔이 생긴다. 이게 또 O(n)이라 복잡도는 그대로다.

> [!warning] 알아채는 신호
> dict를 도입했는데 `.items()`, `.values()`, `for k, v in d` 를 **반복문 안에서** 돌고 있다면
> 해시를 반쪽만 쓰고 있는 것이다. dict를 쓴 이유(O(1) 조회)가 그 줄에서 무효가 된다.

**해결: 없는 방향을 따로 만들지 말고, 이미 갖고 있는 리스트를 그 방향으로 쓴다.**

```python
d = {v: i for i, v in enumerate(lst)}   # 값 -> 위치
# lst 는 이미 위치 -> 값

i = d[x]                                 # 값 -> 위치  O(1)
y = lst[i-1]                             # 위치 -> 값  O(1)

lst[i-1], lst[i] = lst[i], lst[i-1]      # 리스트 갱신
d[x], d[y] = i-1, i                      # dict 도 같이 갱신  ← 빠뜨리면 조용히 틀린다
```

핵심은 **둘을 항상 짝으로 갱신**하는 것. 하나만 고치면 두 자료구조의 내용이 어긋나는데,
에러가 나지 않고 **틀린 답만 조용히 나오기 때문에** 디버깅이 훨씬 어렵다.

> [!tip] 값이 인덱스인 dict를 다룰 때
> "앞으로 간다"가 `+1` 인지 `-1` 인지 매번 헷갈린다면, **저장한 게 순위인지 인덱스인지**를 먼저 확인한다.
> 1등이 0인 인덱스라면 앞으로 가는 건 `-1` 이다.
