## 무엇을 틀렸나

### 1. k개가 모이기 전을 생각하지 않았다 — IndexError

```python
heapq.heappush(slist, i)
answer.append(heapq.nlargest(k, slist)[k-1])
```

```
IndexError: list index out of range
```

**`nlargest(k, ...)` 는 k개를 보장하지 않는다.** 원소가 k개보다 적으면 **있는 만큼만** 돌려준다.
`nlargest(3, [10])` 의 길이는 3이 아니라 1이다. 그런데 코드는 언제나 `[k-1]` 자리를 집었다.

그래서 **첫날부터** 터진다. k일째가 되기 전까지는 그 자리가 아예 없다.

문제 설명이 "k일째부터는 k등의 점수, 그 전에는 가장 낮은 점수" 라고 두 경우를 나눠 말하는데,
코드는 **뒤쪽 경우만** 옮겨 적은 셈이다.

**왜 그렇게 생각했나**

<!-- 이 방식으로 짤 때 머릿속에 있던 전제를 적을 것 -->

**해결**

힙에 **k개만 남긴다.** 넘치면 버린다.

```python
heapq.heappush(hlist, s)
if len(hlist) > k:
    heapq.heappop(hlist)     # 최소 힙이므로 가장 작은 것이 버려진다
answer.append(hlist[0])
```

- 버려지는 게 항상 최솟값이므로, 힙에 살아남는 k개가 곧 **지금까지의 상위 k개**다
- 최소 힙이니 `hlist[0]` 은 그 k개 중 꼴찌, 즉 **k등의 점수**다
- 아직 k일이 안 됐으면 `len(hlist) > k` 가 거짓이라 아무것도 버리지 않고, `hlist[0]` 은 그때까지의 최솟값이 된다

**두 경우를 나눌 필요가 없어진다.** `IndexError` 를 냈던 그 경계가 저절로 맞아떨어진다.
→ [[heapq]] 의 "크기 k 를 유지한다" 패턴

## 이렇게 했으면 어땠을까

### 1. 인덱스만 고친다면 (최소 수정)

```python
answer.append(heapq.nlargest(k, slist)[-1])      # [k-1] 대신 [-1]
```

`nlargest` 는 **내림차순**으로 준다. 그러니 우리가 원하는 값은 **언제나 맨 마지막**이다.

- k개가 다 모였으면 마지막이 k등
- 아직 덜 모였으면 마지막이 그때까지의 최솟값

**두 경우가 같은 자리에 있다.** `if` 없이 인덱스 하나로 끝난다. 이것만으로도 통과한다.

다만 매일 `nlargest` 를 부르면 **그날까지 쌓인 점수 전체를 다시 훑는다.**

| 방식 | 하루당 | 전체 |
|---|---|---|
| 매일 `nlargest(k, 전체)` | O(n log k) | O(n² log k) |
| 크기 k 힙 유지 | O(log k) | O(n log k) |

이 문제는 점수가 최대 1000일치라 둘 다 통과한다. 하지만 **필요한 건 k등 하나인데 전체를 들고 있을 이유가 없다.**

### 2. 매일 정렬한다면

```python
answer.append(sorted(seen, reverse=True)[:k][-1])
```

힙 없이도 풀린다. 하루당 O(n log n) 이라 위 두 방식보다 느리고, 입력이 커지면 가장 먼저 무너진다.
**"매번 전체 순서가 필요한가, 맨 끝 하나만 필요한가"** 가 정렬과 힙을 가르는 기준이다.

## 배운 것

1. `nlargest(k, ...)` / `nsmallest(k, ...)` 는 **k개를 보장하지 않는다.** 있는 만큼만 준다
2. 문제 설명이 경우를 둘로 나눠 말하면, 코드도 그 경계를 처리했는지 확인한다. **첫날·빈 입력처럼 "아직 모이지 않은 때"** 가 늘 함정이다
3. 자료구조를 잘 고르면 **경계 처리가 사라진다.** `if` 로 막기 전에 구조로 없앨 수 있는지 본다
4. 최소 힙으로 **상위** k개를 유지할 수 있다. 버리는 쪽이 최솟값이기 때문이다
